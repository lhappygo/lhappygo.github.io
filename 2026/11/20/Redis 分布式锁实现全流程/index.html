1. 开场：一道面试题的连环追问

简历上写着精通 Java、精通 Redis、精通高并发，面试官只问一句：让你设计一个分布式锁，你会怎么做？

多数人憋半天只能蹦出几个词——setnx、Lua 脚本、看门狗机制。再往下追问就接不住了：看门狗是个什么样的线程？锁的可重入怎么实现？主从架构带来的锁丢失问题怎么解决？最后一个问题，甚至有人反问“锁丢失问题是什么”。

这三个追问，恰好对应分布式锁从“能用”到“生产可用”的三道坎。

2. 锁的本质：互斥

要实现分布式锁，先回答什么是锁。

一个线程拿到锁，另一个线程就拿不到，也就不能继续往下走——这就是锁的互斥性。分布式锁的第一目标同样如此：同一时刻只允许一个客户端（线程）持有锁。

3. 最小可用版：SETNX 加锁

在 Redis 里实现互斥，最直接的方式是 SETNX（SET if Not eXists）：key 不存在时写入成功，视为加锁成功；key 已存在则加锁失败。

3.1 解锁：先判断再释放，用 Lua 保证原子性

加锁之后要解锁。解锁不能直接 DEL，得先判断这把锁是不是当前线程持有的，避免释放错锁——把别人的锁删掉。判断和释放是两步操作，中间锁可能刚好过期并被其他线程拿走，因此必须保证原子性。做法是把“判断持有者 + 删除”写进一段 Lua 脚本，交给 Redis 单线程一次执行完。

3.2 为什么 SETNX 反而不需要放进 Lua

面试常追问：既然原子性要靠 Lua 脚本，为什么加锁的 SETNX 不写进脚本？因为 SETNX 本身就是一条命令，而 Redis 执行命令是单线程的，单条命令天然具备原子性，不需要额外包裹。

3.3 持有者挂了怎么办：加锁同时设过期时间

一个线程拿到锁之后挂了，它就永远无法主动释放锁，这把锁会被永久占住。所以加锁时必须同时给锁设置过期时间，即便持有者异常退出，锁也能自动释放。

3.4 业务没跑完锁先过期：看门狗定时续期

过期时间又带来新问题：业务还没执行完，锁先超时自动释放了，别的线程就能拿到锁，互斥被破坏。

解法是加一个看门狗线程，定时给锁续期，保证锁不会在业务执行期间自动释放。

3.5 看门狗不能比业务活得久：设为守护线程

那如果业务线程挂了，看门狗还在一直续期，锁不就又永远释放不掉了吗？

所以要把看门狗设置为守护线程（daemon）。守护线程的生命周期依附于业务线程，业务线程结束，JVM 会自动终止它——要守护的人都挂了，它自己的存在也就没有意义了。

4. 可重入：同一线程能否重复持锁

下一个追问是可重入。

开发中写递归、写方法嵌套调用很常见：递归方法里获取锁，会让同一线程重复获取同一把锁；方法 A 拿到锁后调用方法 B，而 B 也要拿同一把锁，同样是同一线程多次获取同一把锁。能被同一线程重复获取的锁，就叫可重入锁。

如果把锁设计成不可重入，同一线程第二次获取就会失败，甚至一直阻塞下去，形成自己把自己死锁的局面。

4.1 其他锁是怎么做可重入的

synchronized 给每个对象关联一个监视器（monitor），监视器里有一个锁计数器字段：重入一次加一，释放一次减一，减到零锁才真正释放完毕。

ReentrantLock 基于 AQS 实现，AQS 里有一个 state 字段，同样充当锁计数器：重入加一，释放减一。

4.2 方案一：Redis Hash 结构 + 重入次数

思路完全一致，分布式锁也要有一个“锁计数器”，只是计数器放在 Redis 里。

  • key：要锁的对象
  • field：线程 id + UUID
  • value：重入次数

重入一次 value 加一，释放一次减一，减到零才真正删除 key。这正是 Redisson 的实现方式——用 Hash 结构、用 hsetnx 写入，而不是 setnx。所以“Redisson 底层就是 setnx”这个说法是错的。

为什么 field 要拼接 UUID？因为集群环境下不同节点上的线程 id 可能重复，只靠线程 id 无法唯一标识持有者，必须拼上 UUID 才能保证唯一性。

4.3 方案二：Redis 存 String，服务内部维护 ConcurrentHashMap

有些公司仍用 Redis 的 String 结构加锁，但在服务内部维护一个 ConcurrentHashMap，map 里的 value 充当锁计数器，重入一次加一次。两种方案都能实现可重入，区别只在于计数器放在 Redis 还是放在本地内存。

5. 阻塞：没抢到锁的线程怎么办

第三个细节：没抢到锁的线程不该直接失败返回，而是等待一会儿再重新抢锁，这就是阻塞锁。

ReentrantLock 的做法是让没抢到锁的线程自旋，不断尝试获取，一旦锁被释放就能拿到并执行任务。

分布式锁同样可以这样自旋重试，有些公司内部就是这么实现的。Redisson 走的是另一条路，利用 Redis 的发布订阅机制：

  1. 没抢到锁的线程订阅一个频道，然后阻塞等待。
  2. 抢到锁的线程执行完任务后发布一条消息。
  3. 之前订阅的线程收到消息被唤醒，重新抢锁。
  4. 仍没抢到的继续订阅，等待下一次发布。

整个过程中用超时时间兜底，避免抢不到锁却无限等待。

6. 主从架构下的锁丢失

可重入、阻塞都实现了，就万无一失了吗？还没有，架构层面还有一个坑。

Redis 常见部署是一主多从。客户端 SETNX 写入主节点成功，主节点还没来得及把数据同步到从节点就宕机了，集群重新选主，某个从节点被提升为新的主节点。此时新主节点上根本没有这把锁的数据，其他线程照样能加锁成功——同一时刻两个客户端同时持锁，互斥性被破坏。

这就是主从架构带来的锁丢失问题。

6.1 Redis 的连锁方案：所有主节点都加锁才算成功

Redis 有一层应对机制，要求部署多个主节点（多主或多主多从），每次加锁必须给所有主节点都加上锁，全部成功才算加锁成功。这样即使某个主节点没来得及同步就宕机，其他主节点上仍有锁数据，新来的线程无法在所有主节点上加锁成功，就只能加锁失败。

代价也很明显：只要一个主节点网络延迟大、加锁很慢，或者某个主节点挂了，整体加锁就会失败，失败概率很高；失败之后还要回滚其他节点上已加上的锁，性能很差。

7. 红锁 RedLock 及其局限

于是官方又提出红锁（RedLock）：同样要求部署多个主节点，但只需要半数以上节点加锁成功，就算加锁成功。

为什么是半数以上？如果你了解过分布式一致性算法，就能明白这里的多数派原理：当某个客户端在超过半数的节点上加锁成功，其他客户端就不可能同时在超过半数的节点上加锁成功，两组集合必然有交集，互斥性因此成立。

RedLock 对加锁时间还有严格要求：某个节点在规定时间内加不上锁就不再等它。反正只要半数以上成功就够，放弃一两个比较慢的节点是无所谓的，这样也不会被单个慢节点拖死整体流程。

那这样就完全没有问题了吗？仍然不是。

  • RedLock 对时间的要求很严格，但不同节点的系统时钟可能出现不一致，所以依然可能出错。
  • Java 有 GC，GC 会暂停线程（STW），导致看门狗无法按时给锁续期，锁在业务执行期间就过期了。
  • 红锁要求部署多个 Redis 主节点，运维复杂，多主节点之间的数据一致性也要额外保证。

所以红锁在实际生产中并不常用。大多数公司要么自己手写一个简单的分布式锁，要么直接使用 Redisson。

把“互斥 → 原子解锁 → 过期与续期 → 可重入 → 阻塞 → 主从丢锁 → 红锁的局限”这条链路完整讲清楚，才算真正理解了分布式锁。

8. 面试速记：九个环节一张表

环节 要解决的问题 常见做法
加锁 同一时刻只允许一个线程持锁 SETNX（SET if Not eXists）
解锁 不能释放别人的锁，判断与删除要原子 判断持有者 + 删除，写进 Lua 脚本
过期时间 持有者宕机后锁能自动释放 加锁时一并设置过期时间
锁续期 业务没执行完、锁先到期 看门狗线程定时续期
看门狗生命周期 业务线程已死，续期必须停止 设为守护线程（daemon），随业务线程终止
可重入 同一线程重复获取同一把锁 Hash 结构，field = 线程 id + UUID，value = 重入次数（hsetnx）；或本地 ConcurrentHashMap 计数
阻塞 没抢到锁不应直接失败 自旋重试；Redisson 用发布订阅唤醒，配超时兜底
主从丢锁 主节点未同步就宕机，新主无锁数据 多主部署，所有主节点都加锁成功才算成功
红锁 RedLock 全主节点加锁失败率高、回滚成本大 半数以上节点成功即成功；仍有系统时钟不一致、GC 暂停导致续期失效、运维复杂等问题
